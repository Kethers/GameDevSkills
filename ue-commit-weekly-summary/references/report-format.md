# 报告格式参考

## 三层结构模板

### 第一层：提交占比大盘（宏观总览）

将相近模块归组，每组格式：

```
- **分组名称 (英文名列举) — 约 xx%**
  - **核心**：该分组涉及的关键系统/技术
  - **现状**：一句话总结发展趋势
```

### 第二层：模块深度解读

对提交数 >= 5 的模块做深度解读：

```
#### 模块名 — 一句话概括（N次提交，作者：xxx）

**方向1名称**
用 2-5 句话深度总结这个方向做了什么，涵盖技术细节（类名、函数名、机制名称）。
> 价值解读：通俗语言解释技术价值和实际应用意义。

**方向2名称**
...

**关键 commit 引用 + 阅读建议**（可选，仅重要模块）
- 引用 1-3 个最有价值的提交标题
- 给出具体阅读建议（看哪些文件、关注哪些类/函数）
```

对提交数 3-4 的模块用表格：

```
| 模块名 | 提交数 | 核心工作 |
|--------|--------|----------|
| XXX    | 4      | ...      |
```

提交数 < 3 的模块可忽略。

### 第三层：整体趋势总结

用 3-5 条总结本周开发重心和趋势。特别指出 UE6 与 UE5 的差异化方向。

## 报告质量要求

- 总结要有足够信息量和技术深度，不是简单翻译 commit message
- 引用具体类名、函数名、机制名称增加信息密度
- Other 模块从 commit titles 中提取有意义的信息分类总结
- 如能观察到 UE6 与 UE5 差异化方向（新子系统、新架构），特别指出

## 通知分段规则

报告必须拆分为多条 notify，每条控制在 2000 字符以内：

1. 「📊 UE 主分支周度总结 (日期范围) - 总览」：ue5-main 状态 + ue6-main 统计 + 第一层大盘
2. 「📊 UE6-Main 周度总结 - 模块解读(上)」：第二层前半部分（前 3-5 个模块）
3. 「📊 UE6-Main 周度总结 - 模块解读(下)」：第二层后半部分 + 小模块表格
4. 「📊 UE6-Main 周度总结 - 趋势总结」：第三层整体趋势

如果某段仍然太长，进一步拆分。

## Markdown 文件输出

所有 notify 内容整合写入一个 Markdown 文件：
- 文件名：`UE6-main提交记录{since_date}~{until_date}.md`
- 开头：`# UE6-Main 分支提交统计报告` + 日期范围 + 数据源信息
- 如 ue5-main 有提交，在文档开头也包含简要总结
- 额外尝试生成 PDF（失败不阻塞）
